BUILD_LOG.md — How jameshendershott.org Got Built, Step by Step

A chronological build log. Each chapter covers one milestone and walks through what we built, the decisions we made, the syntax and patterns we used, and any bugs we hit along the way.

Audience: someone with little or no experience who wants to learn how a real software project actually comes together. Read top to bottom — each chapter assumes you've read the ones before it.

Companion document: LEARN.md is the topical reference ("here's how to think about X"). This document is the narrative ("here's exactly what we did and why, in order").

How to read this

  1. Read sequentially. Skipping chapters means missing context.
  2. Open the files alongside. Path references are real — open them in your editor while you read.
  3. Try the commands yourself. Code blocks marked bash are commands you can run.
  4. It's OK to not understand everything on first pass. Some concepts are introduced briefly here and unpacked further in LEARN.md. Use the cross-references.
  5. Glossary at the end. Anytime a term appears in bold italic, it's defined in the glossary.

Chapter 0 — Before any code: understanding the ask

The ask

This chapter is reconstructed from the git history that pre-dated the teaching docs. The original commit that started this project:

"Initial commit: Digital portfolio with Next.js, TypeScript, Tailwind, and MDX" — 10a40f2

The underlying need, distilled from the hundred-or-so commits since: a personal site that survives an interview. Not a flashy showcase, not a generic resume page — a portfolio where every claim is something the owner can defend in a code review. The honesty framing ("What I Did vs. What AI Did") on every project page is the heart of it.

What's the actual problem

Three problems, in priority order:

  1. Honesty as a differentiator. AI-assisted coding is universal in
    1. Anyone can ship code. The hard, defensible thing is being able to walk through your own architecture and explain which decisions are yours. The site is structured around that distinction.
  2. A career-changer's resume in one place. 20 years in leadership roles, late entry to CS, recent BS, now incoming MS. The site has to make that arc legible without apologising for it.
  3. Self-hosted-friendly. The owner runs a 44-container homelab. Several of the projects on the site are deployed there, and the site itself should integrate with the homelab idiom without demanding it.

Researching prior art

The pre-existing decisions visible in the repo's package.json and next.config.ts:

  • Next.js 16 App Router — chose static rendering for everything except /api/resume (server-rendered PDF). Sitemap and robots.txt generated by Next at build time, not handcoded.
  • Tailwind CSS v4 — newer version with the @theme token system. Custom colour tokens kept to a minimum; the lofi-Japanese palette (purple, gold, dark) is enforced by the existing tokens.
  • MDX for project case studies — content lives in content/projects/*.mdx and is loaded by src/lib/projects.ts via gray-matter for frontmatter and next-mdx-remote for rendering. Adding a project = dropping a .mdx file. No data file to update.
  • PDFKit for the resume PDF, served on demand from /api/resume. The PDF reads from src/lib/resume.ts — a single TypeScript constant — so the data drives both the rendered /resume page and the downloadable PDF.

The design that fell out

Three structural decisions worth understanding before any further chapter makes sense:

  1. Data files drive output. src/lib/resume.ts is the source of truth for resume content. It's consumed by the rendered page, the PDF endpoint, and (today, manually) the static public/resume.md. Update one place, two surfaces update; the third is on a checklist.
  2. Frontmatter is the schema. Project MDX files use frontmatter (title, date, summary, tags, repo, live, access, thumbnail, draft) to describe themselves. The page templates render whatever the frontmatter says. There's no list of projects to keep in sync — the file system is the list.
  3. Honesty section is non-negotiable. Every project case study has a "What I Did vs. What AI Did" section. This is a content convention enforced by tradition, not a code constraint. The precedent matters more than the mechanism.

Chapter takeaways

  • The site is content-first: most updates are MDX or data, not JSX.
  • Honesty framing is the defensibility strategy. Without it, this is just another portfolio. With it, the site does the interview prep.
  • src/lib/resume.ts is the spine. Touch it, and the PDF, the rendered page, and (manually) the markdown all move with it.

Chapter 1 — April 2026: OMSCS admission and the four-project refresh

📌 What this chapter teaches. How a content-first portfolio absorbs a status change and four new projects in one sweep. Concepts introduced: data-first refactor, in-place rewrite vs. additive change, honesty section as a deliberate structural element, frontmatter as a schema.

The ask

Three things had happened since the last refresh on 2026-02-28:

  1. Admitted to Georgia Tech's OMSCS program — Machine Learning specialization, Fall 2026 start, admitted 2026-04-17. The user provided exact wording: "Master of Science in Computer Science — Georgia Institute of Technology · OMSCS · Machine Learning Specialization · Admitted April 2026 · Fall 2026 start." The OMSCS line had to land at the top of the Education listing in every place education appears. The Weber State BS (Dec 2025, 3.56/3.87 CS) and AAS (Dec 2023) stayed in that order below it. No UX Design minor anywhere — it was never completed and had been removed from prior materials.
  2. Four new projects to add as case studies, each with the existing "What I Did vs. What AI Did" honesty section:
    • labelgen-pro — Vue 3 / TypeScript / Vite filament label generator
    • stash — React Native + Expo + Postgres self-hosted inventory app
    • property-comparison — refresh of an existing case study (same repo)
    • real-estate-video-generator — small Python + FFmpeg desktop tool
  3. Sweep every page that mentioned education or current status and change "applied to" → "admitted to."

The plan

Four constraints from the user shaped the plan more than the asks themselves:

  • "Show me each file diff one at a time, smallest blast radius first." → data files before pages, pages before global config.
  • "Do NOT remove or rename any existing project." → additive only, with one specific exception we'll discuss.
  • "Do NOT modify existing 'What I Didn't Do' honesty sections."
  • "No new dependencies."

Sequence we landed on:

  1. Update src/lib/resume.ts (data; drives PDF + page + checklist for public/resume.md).
  2. Add three new MDX files; rewrite one existing MDX file in place.
  3. Update visible pages: /now, /about, /resume, and the static public/resume.md.
  4. Verify with tsc --noEmit and next build.

The conflict we caught before writing any code: the user asked us to add a property-comparison case study, but content/projects/property-comparison.mdx already existed for the same repo. Adding a second file would either collide on slug or duplicate. We flagged it; user clarified: "the property comparison is the same project but we have the updated version. So just do a re-write where it is." That's the difference between an additive change (new file, no risk to existing content) and an in-place rewrite (overwrite existing file, existing thumbnail path preserved). Catching this before writing code saved us a slug collision and a duplicate visible to readers.

Step 1: Education in src/lib/resume.ts

The education array used to start with the Weber BS. We prepended an OMSCS entry and removed "| Applied to Georgia Tech OMSCS" from the BS bullets (now redundant — OMSCS is its own entry above):

education: [
  {
    school: "Georgia Institute of Technology",
    degree: "M.S. in Computer Science — OMSCS · Machine Learning Specialization",
    bullets: [
      "Admitted April 2026 · Fall 2026 start · 100% asynchronous online",
    ],
  },
  {
    school: "Weber State University",
    degree: "B.S. in Computer Science — December 2025",
    bullets: [
      "GPA: 3.56 overall (3.87 in CS coursework)",
      // (key courses bullet preserved)
    ],
  },
  // ... AAS entry preserved
]

Why this file first. Three surfaces consume resume.ts: the rendered /resume page (only on the page template, indirectly via the same content), the PDF endpoint at src/app/api/resume/route.ts, and (manually) public/resume.md. The route.ts does:

import { resumeData } from "../../../lib/resume";
// ...
r.education.forEach((ed) => {
  doc.font("Helvetica-Bold").fontSize(10).text(`${ed.school}`);
  doc.font("Helvetica").fontSize(10).fillColor("#666").text(ed.degree);
  if (ed.bullets && ed.bullets.length) bulletList(doc, ed.bullets);
});

That loop is order-preserving. Putting OMSCS first in the array means it renders first in the PDF — no code change to the route required. This is what "data drives output" gets us: a structural change expressed once.

Step 2: Four MDX case studies

labelgen-pro.mdx, stash.mdx, and real-estate-video-generator.mdx are new files. property-comparison.mdx was rewritten in place (same slug, same thumbnail path).

Frontmatter pattern for each:

---
slug: <slug>
title: <Title>
date: 2026-04-25     # YYYY-MM-DD; sorts the projects list newest-first
summary: <one-line>
tags: [...]          # Title Case, matching existing convention
repo:    <url>       # OR
access:  mailto:...  # for private repos
thumbnail: "/images/projects/<slug>.png"
---

The repo vs. access choice is a real fork. repo points to a public GitHub URL; access is a mailto: link the page renders as a "Request Access" button. Three of the four new projects are private repos and used access; only property-comparison had a public repo. The page template at src/app/projects/page.tsx renders the right button based on which key is present.

The honesty section. Every existing case study has a "What I Did vs. What AI Did" section. We followed it on every new file:

## What I Did vs. What AI Did

**My work:**
- [Architectural decisions, integration choices, the things you'd
  defend in a code review]

**AI-assisted:**
- [Boilerplate, library idioms, scaffolding]

This is a content convention, not a code constraint. The MDX renderer treats it like any other section. What enforces it is precedent: every prior case study has one, every reader expects one. Changing the convention would require a sweep across all files, so it stays.

Screenshot TODO. Each new MDX has a comment near the top:

{/* TODO: capture screenshot at public/images/projects/<slug>.png — 1280x720, dark mode preferred */}

MDX comments use {/* */} (JSX syntax), not <!-- -->. The user captures the screenshots separately. Until then, the page falls back to a gradient placeholder via the conditional in the projects page template:

{p.thumbnail ? (
  <Image src={p.thumbnail} ... />
) : (
  <div className="...gradient...">Project Screenshot</div>
)}

The placeholder doesn't break the build, doesn't 404 in <Image> (because we never reference a missing file unless thumbnail is set), and the <Image> itself only fails at runtime if the listed file doesn't exist on disk. So the moment those PNGs land in public/images/projects/, the cards light up — no MDX edit needed.

Step 3: Visible pages

Four small edits, smallest blast radius first:

  • src/app/now/page.tsx — bullet list reordered; OMSCS bullet now first; header date moved to April 2026.
  • src/app/about/page.tsx — one prose sentence: "applying to Georgia Tech's OMSCS program" → "was admitted to Georgia Tech's OMSCS program in April 2026 — Machine Learning specialization, starting Fall 2026."
  • src/app/resume/page.tsx — added a new MS-in-CS block above the BS block; removed "| Applied to Georgia Tech OMSCS" from the BS GPA line.
  • public/resume.md — same as the page edit, in markdown.

The public/resume.md edit is the one that bothered us. It's a static file that mirrors structured data in src/lib/resume.ts, which means the two can drift. We didn't fix that today (out of scope), but we flagged it as future cleanup: a small build script that regenerates public/resume.md from resumeData would collapse two sources of truth into one.

Bugs we hit

None during the edits. The risk we caught upfront — the property-comparison slug collision — was the only thing that would have broken something, and we caught it by reading the existing content directory before writing files instead of after.

That's a real lesson: when an instruction says "add four projects," the temptation is to write four new MDX files immediately. Five seconds of ls content/projects/ would have shown the conflict, and five minutes of clarifying with the user saved an hour of "why is the projects page showing two property-comparison cards."

Verifying

npx tsc --noEmit       # clean
npm run build          # success, 29 static pages, 18 project routes

The [+14 more paths] line in the next build output is the SSG log for /projects/[slug]. 15 existing MDX files + 3 net new (one rewrite, not new) = 18 project pages. Math matches.

Chapter takeaways

  • Read the existing content directory before writing new files. Slug collisions are the kind of bug next build doesn't catch — it'll happily generate two pages with the same slug if the file system allows it, and the second one wins silently.
  • Data-first refactors travel. Updating resume.ts's education array updated the PDF, the rendered page, and the data flowing into the static markdown — three surfaces from one edit.
  • Honesty is a structural element, not garnish. The "What I Did vs. What AI Did" section is the load-bearing wall in every case study. Skipping it on a new project would degrade the whole site.
  • Flag conflicts before writing code. When the user's instruction contradicts itself ("add four projects" + "don't rename existing"
    • an existing file with the same name), the cost of asking is one message. The cost of guessing wrong is a half-day of cleanup.

Chapter 2 — April 2026: site audit, plus a parallel skill refactor

📌 What this chapter teaches. How to keep an honest engineering log when a session does no code work on the project but produces durable artifacts (an audit, a backlog) that will shape future sessions. Concepts introduced: audit-as-punch-list, severity-indexed findings, session-honesty principle — if you don't log the sessions where nothing shipped to main, the teaching log slowly turns into a highlight reel and stops teaching.

The ask

Two distinct asks in one session, on different surfaces:

  1. "Audit the site and see where I could make improvements." Then, after the audit landed: "save it into the vault." Then "add an Audits section to the project index with a link to this file."
  2. "While we're here, can you also help me with the home-search skill files? I think one of the other Claude agents may have written something into one of your skills."

The first is portfolio work. The second is unrelated home-search infrastructure work. Both happened in the same conversation. This chapter covers the portfolio side honestly — which means acknowledging that the bulk of the session's effort went elsewhere.

The plan

For the portfolio side specifically:

  1. Walk every page and component, every config file, the global CSS, the data layer.
  2. Produce findings in three buckets — visual design, UX, code structure — with one specific recommendation per finding.
  3. Save the audit as a dated, ID-indexed markdown file in the vault so future commits can reference findings by ID (e.g. "fix(ux): home hero mentions OMSCS (audit U9)").
  4. Update the vault project index to point at the new audit.
  5. Don't ship any audit fixes in this session. That was the user's explicit choice — they wanted the audit written first, then to triage in a separate sitting.

Step 1: The audit itself

Output: D:/James_Journey/projects/active/digital-portfolio/audit-2026-04-29.md (35 KB, 1117 lines, 31 findings).

Findings are indexed by ID — V1–V8 for visual, U1–U10 for UX, C1–C13 for code structure, A1–A7 for accessibility / performance / SEO. Severity scale 🟥/🟨/🟩 (high / medium / low).

The format that worked: each finding is self-contained — file path, current code snippet, suggested change with code example. So a future implementer can act on U9 without re-reading the audit's preamble.

Step 2: The vault index update

D:/James_Journey/projects/active/digital-portfolio/digital-portfolio.md got a new "Audits" section between Recent Updates and TODO. The section is a single-row table:

| Date       | Audit                              | Against commit | Findings                          | Status |
|------------|------------------------------------|----------------|-----------------------------------|--------|
| 2026-04-29 | [[audit-2026-04-29|Site Audit ...]] | `8ee1966`      | 31 (4 high · 12 medium · 15 low) | Open   |

Plus a "Top items from the latest audit" sub-block listing the four high-severity findings. The intent: anyone opening the project index sees both the current state (Recent Updates) and the open backlog (Audits → Top items) at a glance.

Step 3: The honest non-update

The user also asked to refresh two stale lines in the project index:

  • "Recent Updates" had a (PENDING) entry from before this session's commits actually shipped. Updated to a 2026-04-27 entry citing the commit range.
  • The file's *Last Updated* footer was 2026-02-28. Updated to 2026-04-29.

These are tiny edits but they're the kind of thing that visibly rots a project index when neglected. Worth doing.

What didn't happen this session

Nothing portfolio-side actually shipped to main. No audit findings were addressed. The push from Chapter 1 (8ee1966) is still the HEAD. Chapter 2 is a planning chapter. The honest framing matters: a teaching log that only chronicles ship-days drifts into revisionism. Documenting the day where you thought and queued without coding is part of the engineering practice.

The parallel work

For completeness — the bulk of the session's wall-clock time went into refactoring James's home-search skill files (a different project entirely, in C:/Users/James/.claude/skills/). That work introduced a _buyer-profile.md single-source-of-truth pattern, revised the all-in-monthly skill with a "no guessing, worst-case bias" data-sourcing policy, and ran a full property intake for 159 Volley Rd, Ellenboro NC. None of that touched the portfolio codebase, but mentioning it here keeps the timeline truthful — when future-James reads this chapter, the session was not a quiet day.

Verifying

Nothing to verify on the portfolio side — no code changed.

Chapter takeaways

  • An audit is a backlog, not a deliverable. The audit's value isn't in being written; it's in being referenced by future commits. The ID system (U9, C2) makes that reference cheap.
  • Save the audit somewhere durable, not in chat. The vault is the right home — versioned, syncs to Unraid via Syncthing, gets picked up by future sessions reading project state.
  • Log the planning sessions too. A teaching log that only documents code-shipping days drifts into revisionism. The session where nothing shipped but something was decided is exactly the kind of session worth remembering.
  • Cross-project sessions are fine; just be honest about them. When one conversation spans two unrelated projects, each project's log records its own slice. Don't mix them, but don't pretend the other half of the session didn't exist either.

Glossary

Term Meaning
OMSCS Online Master of Science in Computer Science (Georgia Tech). 100% asynchronous, accredited identically to the on-campus MSCS.
Data-first refactor Updating a single source-of-truth data file (here src/lib/resume.ts) and letting downstream renderers (page, PDF) update by re-reading it, instead of editing each rendered surface separately.
In-place rewrite Replacing the contents of an existing file at the same path / same slug, instead of adding a new file. Preserves the URL and any external references; risks losing prior content if not careful.
Additive change Adding a new file or new entry without modifying anything existing. Lowest-risk change type — nothing prior is at risk.
Honesty section The "What I Did vs. What AI Did" subsection on every case study. A content convention, not a code rule, but precedent across all files makes it functionally mandatory.
Frontmatter as a schema Treating the YAML at the top of an MDX file as a typed contract (slug, title, date, summary, tags, repo/access, thumbnail). The renderer page is the schema's enforcer.
MDX Markdown with JSX. Lets us mix component-style elements (e.g. {/* comments */}) into otherwise plain markdown content.
Frontmatter The YAML block at the top of a markdown / MDX file, between two --- lines. Parsed by gray-matter here.
Slug The URL-safe identifier for a page (e.g. labelgen-pro). Derived from the MDX filename. Two files with the same slug collide.
Audit-as-punch-list An audit document treated not as a one-time deliverable but as a referenceable backlog. Findings get stable IDs (e.g. U9, C2) so future commit messages can cite the audit, turning fixes into a checklist that closes over time.
Severity-indexed findings Audit findings tagged with a severity (🟥 high / 🟨 medium / 🟩 low) and grouped at the end into an index. Lets a reader skim the top tier without reading the full document.
Session-honesty principle Log every working session in the build log, including the ones where nothing shipped to main. Skipping the planning / decision-making / pivoting sessions turns the log into a highlight reel and erodes its teaching value.
